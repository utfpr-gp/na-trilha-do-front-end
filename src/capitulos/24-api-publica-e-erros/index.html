Serviço dos outros falha, demora e responde de jeitos inesperados. Por isso, o centro deste capítulo é a regra RN07 do PRD: uma falha num serviço externo nunca impede o resto da página de funcionar. O resultado está em etapas/24-api-publica-e-erros.

Antes de sair para a trilha, o guia escuta o boletim do tempo na rádio da cidade. É um serviço de graça, aberto a todos, que ele não controla: às vezes o sinal falha, às vezes o boletim atrasa. Um bom guia não cancela o passeio por isso. Ele avisa "sem previsão hoje", olha o céu e segue com o resto do planejamento.

Uma API pública é a rádio: você consulta, mas não manda nela. O seu código precisa ouvir com atenção (ler o corpo da resposta, e não só o status) e ter sempre um plano para o silêncio: um aviso só naquela parte da página, e o resto funcionando.

Escolher uma API

Há catálogos com milhares de APIs abertas: a lista Public APIs, a API Ninjas, o RapidAPI Hub e a rede de APIs do Postman. Antes de escolher uma para um site feito só de HTML, CSS e JavaScript, confira cinco coisas:

  • Documentação: os endereços, os parâmetros e um exemplo de resposta;
  • Chave: sem chave é o ideal. Uma chave no código do navegador fica à vista de todo mundo (veja as armadilhas);
  • CORS: a API precisa aceitar chamadas vindas do navegador, com o cabeçalho Access-Control-Allow-Origin;
  • HTTPS: o site publicado é https://, e o navegador bloqueia pedidos para http:// a partir dele;
  • Limites e termos: quantos pedidos por dia, e se é preciso citar a fonte.

A Open-Meteo e o ViaCEP passam nos cinco: gratuitos, sem chave, com CORS e HTTPS. A Open-Meteo pede que a fonte seja citada, e o Trilheiro mostra "Dados: Open-Meteo" junto da previsão.

Os jeitos de dar errado

Um pedido a um serviço externo pode terminar de quatro jeitos ruins, e cada um pede um cuidado:

  • A rede falha (sem internet, serviço fora do ar, CORS): o fetch lança TypeError: Failed to fetch, e o catch pega;
  • O status não é 2xx (400, 404, 500): o fetch não lança nada, e o código confere o response.ok ou o response.status;
  • O status é 200, mas o corpo diz que não deu, como o erro do ViaCEP ou a geocodificação sem o campo results: o código lê o corpo;
  • A resposta não chega: o pedido fica pendurado. Um tempo-limite resolve.
Aprofundando: e as APIs que pedem chave?

Muitas APIs boas (mapas, filmes, clima mais detalhado) exigem uma chave, que identifica quem paga ou quem responde pelo uso. Num site só de front-end, não existe lugar seguro para ela: tudo o que o navegador recebe, a pessoa pode ler. Algumas chaves são feitas para ficar à vista, limitadas ao endereço do seu site (o painel da API diz). Para as outras, o caminho é um back-end seu, que guarda a chave e faz o pedido no lugar do navegador. Esse é um dos motivos para os projetos crescerem para além do front-end.

Tudo o que o navegador baixa, a pessoa lê: a chave aparece na aba Sources e em cada pedido da aba Network. Alguém pode usá-la e gastar a sua cota (ou o seu dinheiro). Prefira APIs sem chave, ou com chave limitada ao endereço do seu site.
