No capítulo 1, o cartão da trilha era um arquivo solto, com o Bootstrap vindo de um CDN. Hoje ele vira um projeto: uma pasta com carteira de identidade (o package.json), o Bootstrap instalado pelo npm, aberta no VS Code, servida pelo Live Server e guardada no Git, com uma cópia no GitHub. O projeto nasce no GitHub e desce para o seu computador, nesta ordem.

Na tela, nada muda: o cartão é o mesmo. O que muda é tudo o que está em volta dele, e é isso que vai acompanhar você até o último capítulo. O resultado está em etapas/02-preparar-o-ambiente.

Ninguém descobre no meio do caminho que esqueceu a água. Antes de sair, você confere a mochila: o que leva, o que fica em casa, e uma lista para não depender da memória.

O package.json é essa lista: diz o que o projeto precisa levar. A pasta node_modules/ é a mochila cheia, que você arruma de novo a partir da lista sempre que precisar. E o Git é o caderno de campo, que anota cada trecho percorrido para você poder voltar a qualquer ponto.

São quatro ferramentas, cada uma com um papel:

  • VS Code: o editor onde você escreve o código. Tem um terminal embutido (menu Terminal → New Terminal), e é nele que você roda os comandos deste livro.
  • Live Server: uma extensão do VS Code que serve a pasta do projeto num endereço como http://127.0.0.1:5500 e recarrega a página sozinho a cada vez que você salva.
  • Node.js e npm: o Node.js roda JavaScript fora do navegador; o npm, que vem junto com ele, baixa bibliotecas como o Bootstrap e anota no package.json o que o projeto usa.
  • Git e GitHub: o Git guarda o histórico do projeto no seu computador, em fotografias chamadas commits; o GitHub guarda uma cópia desse histórico na internet.

O mais importante é entender o caminho que cada arquivo faz:

  1. Registro do npm Onde ficam o Bootstrap e milhares de outras bibliotecas.
  2. npm install →
  3. Seu computador package.json e package-lock.json (a lista) e node_modules/ (os arquivos baixados).
  4. git push →
  5. GitHub O seu código e a lista. A node_modules/ fica de fora, por causa do .gitignore.

A node_modules/ não vai para o GitHub porque não precisa: qualquer pessoa que baixar o projeto roda npm install, e o npm lê o package.json e o package-lock.json e baixa exatamente as mesmas versões. Guardar a lista é suficiente para refazer a mochila.

Qual versão do Node.js?

O site do Node.js oferece duas: a LTS (Long Term Support, suporte por muitos anos) e a Current, a mais nova. Escolha sempre a LTS: ela é estável e recebe correções de segurança por anos. As versões LTS são as de número par.

Como o seu computador prova ao GitHub que é você?

O GitHub não aceita a senha da sua conta no terminal. Para enviar código por HTTPS, você usa um token de acesso pessoal: uma senha longa, gerada pelo próprio GitHub, que vale só para os repositórios e as permissões que você escolher, e só por um tempo. Quando o terminal pedir a senha, você cola o token. No seu computador pessoal, uma alternativa é a chave SSH, que dispensa digitar qualquer coisa a cada envio.

Aprofundando: e se eu precisar de duas versões do Node.js?

Um projeto antigo pode exigir o Node 20, e outro, o 24. O NVM (Node Version Manager) instala várias versões lado a lado e troca entre elas com um comando, como nvm use 24. No Windows, o equivalente é o nvm-windows, instalado à parte.

Aprofundando: por que o npm instalou 2 pacotes, se pedi só 1?

Ao instalar o Bootstrap, o npm também baixa o @popperjs/core, uma biblioteca que o JavaScript do Bootstrap usa para posicionar menus e dicas. O Bootstrap declara essa necessidade no próprio package.json dele, e o npm resolve sozinho. O package-lock.json registra a versão exata de cada um.

No git push, o terminal pede usuário e senha. No usuário, digite o seu usuário do GitHub; na senha, cole o token, nunca a senha da conta. No Linux, nada aparece enquanto você cola, e é normal. No Windows, pode abrir uma janela do Git Credential Manager: escolha a opção de token, ou entre pelo navegador.

Aprofundando: como gerar o token

No GitHub, clique na sua foto, depois em Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token. Dê um nome, escolha a validade, em Repository access marque Only select repositories e selecione o trilheiro, e em Permissions dê à permissão Contents o acesso Read and write (sem ela, o push é recusado). Clique em Generate token e copie na hora: o GitHub só mostra o token uma vez. Guarde num gerenciador de senhas, nunca num arquivo de texto no computador.

Apague a pasta node_modules/ inteira e recarregue o Live Server: o cartão perde o estilo, porque o <link> aponta para um arquivo que não existe mais. Agora rode npm install, sem nome de pacote: o npm lê a lista e refaz a mochila. Recarregue, e o cartão volta.

Os hábitos que evitam dor de cabeça

  • Comece com um git pull origin main. Se você mexeu no projeto em outro computador, ou alguém mexeu por você, o pull traz essas mudanças antes de você escrever qualquer linha.
  • Faça commits pequenos. Terminou uma página? Commit. Corrigiu um erro? Commit. Um commit por mudança deixa fácil voltar atrás no ponto certo.
  • Nunca faça commit da node_modules/ nem de arquivos .env.

Por que a pasta node_modules/ fica fora do Git?

O GitHub aceitaria. Ela fica de fora porque é pesada e pode ser refeita a partir da lista.

A node_modules/ só tem as bibliotecas baixadas. O motivo é outro: ela pode ser refeita com npm install.

O que o Live Server faz que abrir o index.html com dois cliques não faz?

Quem instala o Bootstrap é o npm. O Live Server só serve os arquivos que já estão na pasta.

O endereço do Live Server (127.0.0.1) só existe no seu computador. A publicação é assunto do capítulo 26.

No package.json, o que quer dizer "bootstrap": "^5.3.8"?

Sem o ^ seria exatamente a 5.3.8. O ^ aceita atualizações que mantêm o primeiro número.

A 6.0.0 muda o primeiro número, o que indica mudanças que podem quebrar o código. O ^ não aceita.

Você rodou npm install e apareceu Could not read package.json. Qual é a causa mais provável?

O erro fala de um arquivo local, o package.json, e não de um pacote na internet.

O npm não depende do Live Server. Ele procura o package.json na pasta em que o terminal está.

No git push, o terminal pede a senha. O que você digita?

O GitHub não aceita mais a senha da conta no terminal. No lugar dela vai o token, que vale só para os repositórios e as permissões que você escolheu.

Sem credencial, o GitHub recusa o envio. Cole o token de acesso pessoal.
