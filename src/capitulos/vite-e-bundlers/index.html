No fim da trilha, o Trilheiro funciona, mas o processo para mantê-lo tem remendos: um terminal para o Sass, o Live Server num canto, as bibliotecas vindas de um CDN porque a node_modules não vai para o ar, o cabeçalho copiado em quatro páginas. Projetos que crescem resolvem isso com uma ferramenta de build, e a mais usada hoje no front-end é o Vite.

Neste extra, o Trilheiro da etapa 26 passa a ser montado pelo Vite. Nada muda na tela. Muda o caminho até ela: um servidor de desenvolvimento que compila o Sass sozinho e atualiza a página na hora, as bibliotecas instaladas pelo npm e importadas no JavaScript, e um comando, npm run build, que gera o site pronto e otimizado numa pasta dist/. O resultado está em etapas/extra-vite-e-bundlers.

Em casa, o equipamento fica espalhado: o fogareiro numa prateleira, a lanterna na gaveta, a comida no armário, cada coisa na embalagem original. Antes da trilha, você junta só o que vai usar, tira as embalagens que pesam e arruma tudo numa mochila compacta.

Um bundler faz isso com o site. Durante o desenvolvimento, os arquivos ficam separados e legíveis: os módulos do capítulo 19, os parciais do Sass, os pacotes do npm. No build, ele junta tudo o que as páginas usam, tira o que não é usado, encolhe o código e deixa uma pasta pronta para a viagem.

Dois modos: desenvolver e construir

  • npm run dev: um servidor no seu computador, como o Live Server, mas que entende o que o navegador não entende. Ele compila o .scss no momento em que a página pede, resolve um import 'bootstrap' buscando o pacote na node_modules, e troca só o que mudou quando você salva, sem recarregar a página inteira;
  • npm run build: gera a pasta dist/, com o HTML, um CSS e alguns JavaScripts já juntos, encolhidos e com um código no nome (format-BumuxZ1i.css). Quando o arquivo muda, o nome muda, e o navegador nunca usa uma cópia velha do cache.

Foi o que o Trilheiro ganhou, comparado com a etapa 26:

  • o HTML aponta direto para o scss/main.scss, e o css/main.css compilado à mão deixou de existir;
  • o Bootstrap, os ícones, o jQuery e o plugin de máscara vêm do npm, com import, e vão para o dist/ junto com o resto: não há mais CDN nem globais como o $;
  • a imagem do topo, pequena, foi embutida no próprio CSS, e as fontes dos ícones foram copiadas com o código no nome.

A pasta public

O Vite só sabe de um arquivo quando algum código o cita de forma que ele consiga ler: um import, um href no HTML, um url() no CSS. As fotos do Trilheiro são montadas pelo JavaScript a partir do nome que vem do db.json (`img/trilhas/${photo.arquivo}-480.webp`), e esse texto o Vite não tem como adivinhar. O que vai para a pasta public/ é copiado para o dist/ como está, sem código no nome: é o lugar das fotos, do ícone da aba e do db.json.

Aprofundando: e o cabeçalho repetido?

O Vite, sozinho, não junta pedaços de HTML: as quatro páginas continuam com o cabeçalho copiado. Isso se resolve com um plugin do Vite que inclui parciais, ou com um framework que monta as páginas a partir de componentes. Este livro, por exemplo, é feito com o Vite e um plugin próprio que troca marcadores como <!-- @include header --> pelo cabeçalho, em todas as páginas. Frameworks como o Angular, o React e o Vue vão além: a página inteira vira uma árvore de componentes.

O Vite procura o pacote na node_modules e não acha. Confira o nome no import e se ele está no package.json; depois de clonar o projeto, rode npm install.

Imagens citadas só por um texto montado no JavaScript não são vistas pelo Vite e não vão para o dist/. Guarde-as em public/. A mesma coisa vale para o db.json, que o modo publicado lê com fetch.

Pelo file://, os módulos não carregam (capítulo 19), e a página fica sem cartões. Use o npm run preview, que serve o dist/ por http://.

Com o Vite, a raiz do projeto tem o código-fonte, que o navegador não entende (o .scss, os import 'bootstrap'). O que vai para o ar é o dist/, gerado pelo build. E o dist/ fica no .gitignore: ele é refeito a cada build.
O que o npm run build do Vite produz?

O dist/ é um site estático: qualquer servidor de arquivos, como o GitHub Pages, serve.

O build faz bem mais: junta o JavaScript, as bibliotecas e o CSS, e põe tudo no dist/.

Por que as fotos do Trilheiro ficam em public/?

Aceita, e até otimiza, quando a imagem é citada no HTML, no CSS ou num import.

É o contrário: o que está em public/ é copiado como está e fica acessível no site.

Por que o nome do arquivo gerado tem um código, como format-BumuxZ1i.css?

O nome está no HTML, à vista. O código serve para o cache.

O nome não muda o tamanho. Ele muda quando o conteúdo muda.

Com o Vite, o ESLint ainda precisa do $ nos globals?

Os globals eram para o que vinha de um <script> comum. Com o import, o nome é declarado no próprio arquivo.

Os dois são independentes: o ESLint continua rodando com npm run lint.

Se quiser ir além no seu projeto, faça a migração numa branch: instale o Vite, configure as páginas, troque o CDN por import e o CSS compilado pelo Sass direto. Rode o build, confira com o preview e publique o dist/.
