O link "Cadastrar trilha" do menu, parado desde o capítulo 9, ganha a sua página: cadastrar.html, com um formulário para uma trilha nova. E um formulário só presta se recusa dados errados. Por isso, cada regra do PRD vira uma conferência no navegador: o nome com 3 a 80 caracteres (RN01), a distância de 0,5 a 50 km com uma casa decimal (RN02), a dificuldade e o percurso escolhidos entre as opções (RN03), o CEP e o telefone no formato certo (RN04), a data da última visita nunca no futuro (RN05).

Cada erro aparece logo abaixo do campo, em português claro e no vermelho de "Difícil", só depois que a pessoa passou pelo campo ou tentou salvar. Quando está tudo certo, o formulário monta o objeto da trilha, pronto para ser gravado quando o servidor chegar. O resultado está em etapas/20-validar-formularios.

Na portaria do parque, o guarda confere o básico de quem entra: tem água? Tem calçado fechado? Para quem vai à trilha difícil, pergunta mais. E ele não espera a pessoa chegar no meio do caminho para avisar que falta lanterna: avisa ali, na hora, com uma frase clara.

A validação é esse guarda. Os atributos do HTML (required, min, pattern) conferem o básico de graça; o JavaScript entra para as regras especiais e para falar como gente. Uma ressalva: o guarda da portaria não substitui a segurança do parque. Quem tem um servidor confere de novo lá, porque o navegador está nas mãos de quem visita.

O HTML já valida

Só com atributos, sem uma linha de JavaScript, o navegador recusa o envio e mostra um balão junto do primeiro campo com problema:

  • required: não pode ficar vazio. Num grupo de rádios, basta no primeiro;
  • minlength e maxlength: o tamanho do texto;
  • min, max e step: os limites de um número ou de uma data. O step="0.1" aceita uma casa decimal;
  • type="email", type="number", type="date": o tipo do valor, com o teclado certo no celular;
  • pattern: uma expressão regular que o valor inteiro precisa seguir.

Aprofundando: por que validar de novo no servidor?

Qualquer pessoa pode abrir o DevTools, apagar o required e enviar o formulário vazio, ou mandar os dados direto para o servidor, sem passar pela página. A validação no navegador existe para ajudar quem preenche, com a resposta na hora. A que protege os dados é a do servidor. O json-server do capítulo 23 não confere nada: num projeto de verdade, o back-end repete as regras.

Tire a primeira linha do validateField, o field.setCustomValidity(''). Digite "123" no nome, saia do campo, e depois corrija para "Trilha 123": o erro "O nome precisa ter letras." não sai mais, e o formulário nunca é aceito. Desfaça.

Depois de um setCustomValidity('mensagem'), o campo continua inválido até alguém chamar setCustomValidity(''). Sempre comece a conferência apagando o erro anterior.

O Chrome lê o pattern com uma regra mais rígida (a flag v), em que um hífen solto entre colchetes não vale. O pior: com o pattern inválido, o navegador simplesmente ignora a regra, e qualquer valor passa. Escape o hífen, [0-9\-], e confira o console sempre que mexer num pattern.

O minlength e o maxlength só são conferidos depois que a pessoa digita. Um valor posto pelo JavaScript (campo.value = 'Ab') passa sem tooShort. Para testar, digite no campo, como quem usa o site.

Com o novalidate, o navegador não barra mais nada: o submit acontece sempre, e quem decide é o seu código. Esqueceu o event.preventDefault(), ou o return depois de achar um erro, e o formulário segue adiante.

Conferir no input desde o começo pinta o campo de vermelho na primeira letra ("Use pelo menos 3 caracteres" quando a pessoa digitou só o "T"). Espere o campo ser tocado (focusout) ou a tentativa de salvar, como pede o design system.
Quais valores a expressão /^\d{5}-?\d{3}$/ aceita?

O ? deixa o hífen opcional: sem ele também combina.

O ^ e o $ exigem que o texto inteiro seja o CEP, sem nada antes nem depois.

Um campo com min="0.5" recebeu 0.2. Que problema o validity aponta?

O campo não está vazio. O valor existe, mas está abaixo do mínimo.

O overflow é passar do máximo. Abaixo do mínimo é underflow.

Para que serve o setCustomValidity(''), com o texto vazio?

As regras do HTML continuam valendo: um campo required vazio segue inválido.

A validação continua: o novalidate só tira os balões e o bloqueio automático do envio.
