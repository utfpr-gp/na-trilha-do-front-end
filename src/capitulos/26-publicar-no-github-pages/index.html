Até aqui, o Trilheiro só existiu no seu computador, em 127.0.0.1:5500. Hoje ele ganha um endereço na internet, como https://seu-usuario.github.io/trilheiro/, que você pode mandar para qualquer pessoa, e que abre no celular dela.

Publicar um site estático é fácil; o trabalho está no que muda quando ele sai do seu computador. O GitHub Pages só serve arquivos: não roda o json-server nem tem a pasta node_modules. Por isso, o api.js ganha um modo publicado, que lê as trilhas direto do db.json e avisa que cadastrar só funciona no computador; o JavaScript do Bootstrap e os ícones passam a vir de um CDN; e a aba do navegador ganha o ícone do Trilheiro. O resultado está em etapas/26-publicar-no-github-pages.

No escritório do parque, o guia tem tudo: o caderno de registros, o rádio, o telefone para marcar passeios. Na entrada, há um mural com as trilhas, as fotos e os mapas, aberto para quem passar. O mural mostra tudo o que está no caderno, mas não dá para marcar passeio nele: para isso, só no escritório.

O GitHub Pages é o mural: mostra os arquivos do seu repositório para o mundo, mas não roda nenhum servidor. O site publicado lê o db.json como quem lê o mural; gravar continua sendo coisa do escritório, o seu computador com o json-server.

O que é um site estático

O GitHub Pages publica um site estático: pega os arquivos de um repositório e os serve como estão: o navegador pede trilha.html, e recebe o trilha.html. Não há programa nenhum rodando do lado de lá. Isso basta para HTML, CSS, imagens e JavaScript, porque todo o trabalho deles acontece no navegador de quem visita. Mas não serve para nada que precise de um servidor, como gravar um relato.

Três consequências para o Trilheiro:

  • O node_modules não vai junto. Ele está no .gitignore desde o capítulo 2 (e não deve ir: são milhares de arquivos). Tudo o que as páginas usavam de lá passa a vir de um CDN, com a versão fixa no endereço;
  • O CSS compilado vai. O navegador não lê .scss: o css/main.css que o Sass gera precisa estar no repositório, atualizado;
  • Não há json-server. O site publicado lê o db.json como um arquivo comum, com fetch('db.json'), e não grava nada.

Um código, dois modos

O architecture.md já previa isso, na seção 6: o api.js escolhe o modo pelo endereço. Em localhost ou 127.0.0.1, fala com o json-server; em qualquer outro, lê o db.json. Aprofundando: e quando o projeto tem uma etapa de build?

O Trilheiro vai para o ar do jeito que está no repositório. Projetos com uma ferramenta de build, como o Vite (veja "Para ir além"), geram uma pasta dist com o site pronto, e é ela que precisa ser publicada. O pacote gh-pages faz isso: copia a pasta para uma branch separada, gh-pages, e o GitHub Pages é configurado para servir essa branch.

Outro caminho, comum em projetos maiores, é o GitHub Actions: um roteiro que roda no próprio GitHub a cada push, faz o build e publica. É assim que este livro vai para o ar.

No GitHub, abra o repositório e vá em Settings → Pages. Em Build and deployment, escolha Deploy from a branch, a branch main e a pasta / (root), e clique em Save. Em um ou dois minutos, a aba Actions mostra o "pages build and deployment" com um ✓, e o endereço aparece no alto da página de Pages.

Volte o <script> do Bootstrap do index.html para o endereço da node_modules e renomeie a pasta node_modules para node_modules-fora: é o que o GitHub Pages enxerga, nada. Recarregue: o console mostra o 404 do arquivo, e o menu do celular (o botão de três linhas, numa tela estreita) para de abrir. Desfaça as duas coisas.

As três causas mais comuns: um arquivo que vem da node_modules (que não está no GitHub); um caminho começando com /; ou um nome com maiúscula diferente, como img/Salto.jpg para o arquivo salto.jpg. No Windows e no macOS, o nome com maiúscula diferente funciona; no servidor do GitHub, não. Abra o site publicado com a aba Network do DevTools e procure as linhas em vermelho.

Se o api.js mandasse o site publicado falar com http://localhost:3000, ele funcionaria no seu navegador, enquanto o seu json-server estivesse rodando. Para qualquer outra pessoa, localhost é o computador dela, onde não há servidor nenhum. Teste sempre o site publicado com o json-server parado, ou em outro aparelho.

O GitHub Pages serve o css/main.css, e não o .scss. Rode npm run sass antes do commit, para o CSS compilado ir junto. A mesma coisa vale para o db.json: o site publicado mostra o que estava nele no último push.

Num plano gratuito, o GitHub Pages exige um repositório público. Confira também se a branch e a pasta escolhidas existem e se há um index.html na raiz. Depois de salvar, espere o ✓ na aba Actions: antes disso, o endereço responde 404.

O navegador guarda uma cópia dos arquivos (o cache). Depois de um push, espere o ✓ em Actions e recarregue com Ctrl+Shift+R, que ignora o cache.
